# Deployment guide

## Topology

```
            ┌──────────────┐ /api/v1 proxy ┌──────────────────┐
  users ───►│ web (Next.js)│──────────────►│ api (FastAPI ×N)  │──┐
            └──────────────┘               │ + /mcp            │  │     ┌────────────────────┐
  MCP clients ────────────────────────────►│ + 60 s scheduler  │  ├────►│ PostgreSQL 16       │
  providers ─ webhooks ───────────────────►└──────────────────┘  │     │ jobs queue, state,  │
                                                                   │     │ RLS, audit chain    │
                 ┌───────────────────────────────────────┐         │     └────────────────────┘
                 │ worker ×N  (python -m app.workers.runner│─────────┤     ┌────────────────────┐
                 │  --concurrency 4; FOR UPDATE SKIP LOCKED)│         └────►│ Object storage (S3)│
                 └───────────────────────────────────────┘               └────────────────────┘
          Redis: rate limits across API replicas (and the broker if WORKER_MODE=celery)
```

api and worker run the same image with different commands. The default production mode is
`WORKER_MODE=db`: the job queue is a PostgreSQL table, so there is no broker to operate and a
job is committed atomically with the state change that created it. `WORKER_MODE=celery` is
still supported (workflows via Redis; each Celery worker process also drains the DB queue for
Copilot turns and bulk items).

## Render / Vercel (hosted demo)

The quickest hosted setup is the API on **Render** (it needs a long-running process for the
in-process job workers, which serverless platforms do not provide) and the dashboard on
**Render or Vercel**. The database stays on **Neon**.

### 1. API (and optionally the dashboard) on Render

1. Push the repo to GitHub.
2. Render → **New → Blueprint** → select the repo. Render reads [`render.yaml`](../render.yaml)
   and creates `opspilot-api` and `opspilot-web` in the **ohio** region (next to Neon
   `aws-us-east-2`, so database round trips are ~1-2 ms instead of ~300 ms from India).
3. Fill in the prompted secrets:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Neon **direct** connection string (`…neon.tech/neondb?sslmode=require`) |
   | `GEMINI_API_KEY` | key from https://aistudio.google.com/apikey |
   | `DEMO_PASSWORD` | a new strong password for the demo accounts (the public default is in this repo, so never use it online) |
   | `OPSPILOT_API_ORIGIN` (web) | `https://opspilot-api.onrender.com` (the API service URL; check its name in Render) |

   `SECRET_KEY` and `WEBHOOK_SIGNING_SECRET` are generated by Render. `ENCRYPTION_KEY` is
   optional (a stable key is derived from `SECRET_KEY`); set one if you will store live
   integration credentials:
   `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
4. Every boot runs `alembic upgrade head` and the idempotent demo seed, then starts uvicorn.
   Sign in at the `opspilot-web` URL with tenant `acme-demo`, e.g. `admin@acme-demo.test`, and
   your `DEMO_PASSWORD`.

The MCP endpoint is `https://<api-host>/mcp`; the Render hostname is trusted automatically.

**Free-plan notes:** free services sleep after ~15 min idle (the first request then takes about
a minute), and queued jobs pause while the API sleeps. Uploaded document files live on the
instance disk and are lost on redeploy (text and search chunks are in Postgres); use
`DOCUMENT_STORAGE_BACKEND=s3` for durable files. If the local `.env` and Render share the same
Neon database, a seed run with a different `DEMO_PASSWORD` rotates the demo passwords for both;
use a separate Neon branch for production, or set the same `DEMO_PASSWORD` locally.

### 2. Dashboard on Vercel (instead of `opspilot-web` on Render)

1. Vercel → **Add New → Project** → import the repo.
2. **Root Directory:** `frontend` (framework preset Next.js is detected; keep the default build).
3. Environment variable: `OPSPILOT_API_ORIGIN` = your Render API URL.
4. Deploy. The browser only talks to the Vercel origin; `/api/v1/*` is proxied server-side to the
   API, so no CORS setup is needed. The proxy function allows up to 60 s per call (`maxDuration`).

If you use Vercel for the dashboard, delete the `opspilot-web` service in Render (or remove it
from `render.yaml`).

## Production prerequisites (checked by `/health/ready`)

| Requirement | Why |
|---|---|
| `APP_ENV=production` | enables strict config validation |
| `DATABASE_URL=postgresql+psycopg://…` (managed Postgres, TLS) | SQLite is dev-only |
| `SECRET_KEY` ≥ 32 random bytes | JWT signing (local issuer) |
| `ENCRYPTION_KEY` (Fernet) | integration credentials at rest; **rotate = re-encrypt** (see below) |
| `WORKER_MODE=db` + ≥ 1 `app.workers.runner` process (or `celery` + `REDIS_URL`) | durable queue across nodes |
| `REDIS_URL` | shared rate limits across API replicas |
| `MCP_ALLOWED_HOSTS` includes your public API host | the `/mcp` endpoint rejects unknown Host headers |
| `OIDC_ISSUER`, `OIDC_JWKS_URL`, `OIDC_AUDIENCE`, `ALLOW_PASSWORD_LOGIN=false` | SSO instead of local passwords |
| `LLM_PROVIDER=anthropic|openai` + key | otherwise agents run on heuristics only (flagged in readiness) |
| `DOCUMENT_STORAGE_BACKEND=s3` + bucket | durable document storage |
| TLS termination at the load balancer / ingress | encryption in transit |
| Secrets from a secrets manager (AWS Secrets Manager, Vault, GCP Secret Manager…) injected as env vars | never bake secrets into images or `.env` files in repos |

## Database

```bash
alembic upgrade head          # creates schema, then applies PostgreSQL hardening:
                              #   - CREATE EXTENSION vector
                              #   - row-level security policies on all tenant tables
                              #   - role opspilot_app with UPDATE/DELETE revoked on audit_events
python -m app.cli seed        # optional: demo tenant (do NOT seed in production)
```

Run the API and workers as the least-privilege role so RLS is enforced:

```sql
CREATE USER opspilot_svc WITH PASSWORD '…' IN ROLE opspilot_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO opspilot_app;
```

Migrations run as the owner role (bypasses RLS). Connection pool: `DB_POOL_SIZE` per process;
use PgBouncer (transaction mode) when running many API replicas.

### Backup and recovery

* Managed Postgres: enable automated snapshots + point-in-time recovery (WAL). Target RPO ≤ 5 min.
* Object storage: versioning + lifecycle rules; documents are referenced by `storage_key`.
* Redis holds only in-flight task messages; workflow state is in Postgres, so Redis loss is
  recoverable: after restore, `recover_stale_runs` (maintenance job) re-enqueues interrupted runs.
* Restore drill: restore snapshot → `alembic current` must equal `head` → start one worker →
  verify `/health/ready` and that `waiting_approval` runs resume after a decision.

### Encryption key rotation

```python
# one-off script: decrypt with old key, encrypt with new, in a transaction
from cryptography.fernet import Fernet, MultiFernet
old, new = Fernet(OLD), Fernet(NEW)
for row in session.query(Integration).filter(Integration.encrypted_credentials.isnot(None)):
    row.encrypted_credentials = new.encrypt(old.decrypt(row.encrypted_credentials.encode())).decode()
```

## Scaling

| Component | Scale by | Notes |
|---|---|---|
| api | replicas behind LB | stateless; rate limiting uses Redis when available; each replica runs the maintenance scheduler (idempotent; audit sealing takes a per-tenant advisory lock) |
| worker | replicas (`docker compose up --scale worker=N`, k8s `replicas`) × `--concurrency` | claims with `FOR UPDATE SKIP LOCKED`; leases renewed every `JOB_LEASE_SECONDS/3`; a crashed worker's jobs return to the queue when the lease expires; SIGTERM stops claiming and lets running jobs finish (give it a grace period) |
| tenants | `quotas.max_concurrent_runs` (default 25) | a tenant can never hold more running jobs than this, so one tenant's bulk run cannot starve the others |
| LLM | per-agent `token_budget`, tenant monthly token quota | cost is tracked per agent run and per Copilot turn |
| DB | connections: (api replicas × (`DB_POOL_SIZE`+10)) + (workers × (concurrency + 2)) | use PgBouncer in transaction mode when this approaches `max_connections`; read replicas for reports |

Exactly-once guarantees under scale: a job is claimed by one worker at a time; a workflow run
additionally holds an atomic run lease, so a redelivered job can never execute a run twice; a
bulk-run item re-run after a crash may recompute (at-least-once compute) but its side effects
are keyed per item, so it never performs more actions than the first attempt; an interrupted
non-idempotent tool call is verified with the provider before anything is retried.

## Observability

* **Logs**: structured JSON (`LOG_JSON=true`) with `correlation_id` and `tenant_id`; secrets redacted.
* **Metrics**: `/metrics` (Prometheus) — HTTP latency/requests; business KPIs in `daily_metrics`.
* **Traces**: `OTEL_ENABLED=true`, `OTEL_EXPORTER_OTLP_ENDPOINT=…` (FastAPI auto-instrumentation).
* **Alerts** (suggested PromQL/SQL): failed workflows > 0 in 5 min; `incidents.kind = cost_anomaly`;
  circuit-open errors ≥ 5 in 10 min; `approval.tampered` audit events (page immediately).

## CI/CD

`.github/workflows/ci.yml`: ruff → pytest (SQLite, coverage gate) → Alembic up/down/up + smoke
evaluation on PostgreSQL → `pip-audit` → `bandit` → frontend lint/type-check/build → container
builds → Trivy scan (HIGH/CRITICAL fail). Promote images by digest; run `alembic upgrade head` as
a pre-deploy job; roll back by redeploying the previous digest (migrations are additive).

## Scale benchmark

`backend/load/scale_benchmark.py` starts a real API process and real worker **processes** on an
empty database, then: (1) drains a bulk run with 1 and then N worker processes, (2) fires a
burst of concurrent `POST /events` with 20 % exact duplicates, (3) hard-kills one of three
workers mid-batch. After each phase it checks the database for lost items, duplicate side
effects and duplicate workflow runs. `--check` makes it exit non-zero on any violation (CI runs it
on PostgreSQL). It uses the mock LLM and sandbox adapters, so it measures the platform, not a
model provider.

```bash
cd backend
python -m load.scale_benchmark --items 300 --workers 1,4                                   # fresh SQLite file
python -m load.scale_benchmark --items 300 --workers 1,4 --database-url postgresql+psycopg://…/empty_db
```

For HTTP load from several machines against a deployed stack, `load/locustfile.py` ingests events and
polls runs: `pip install locust && locust -f load/locustfile.py --host https://your-api`.

**Measured 2026-10-16** on one Windows laptop (8 logical CPUs). The API, workers, database and
load generator all share that machine. PostgreSQL 16 is local; the LLM is mocked; each worker
process runs 4 jobs at once. Raw output is in `backend/load/scale_results_{sqlite,postgres}.json`.
Numbers vary roughly ±25 % between runs on this machine, so treat them as orders of magnitude,
not SLAs.

| Phase | SQLite (WAL) | PostgreSQL 16 |
|---|---|---|
| 300-item bulk run, 1 worker process | 26.2 s (11.5 items/s) | 21.4 s (14.0 items/s) |
| 300-item bulk run, 4 worker processes | 46.1 s (6.5 items/s): **slower**, one writer at a time | 14.2 s (21.1 items/s); 23.9/s in an earlier run |
| Items lost / failed / duplicate side effects | 0 / 0 / 0 | 0 / 0 / 0 |
| 400 `POST /events`, 32 concurrent clients, 80 exact duplicates, 1 API process | 400 × 202, 80 duplicates detected, 320 runs for 320 unique events; 27.6 req/s, p50 851 ms | same correctness; 29.2 req/s, p50 1.17 s, p95 1.70 s |
| Hard-kill 1 of 3 workers during a 150-item run | 150/150 done, 1 item recomputed, 0 duplicate side effects | 150/150 done, 3 items recomputed, 0 duplicate side effects |

Reading the numbers:

- **Scale-out needs PostgreSQL.** Extra worker processes help on PostgreSQL and hurt on SQLite.
- **Ingestion is CPU-bound per API process.** One process does about 23–31 events/s whatever the client concurrency, so latency under 32 concurrent clients is mostly queueing. With `uvicorn --workers 4`, a separate run measured 68 events/s at concurrency 4. Add API processes or replicas for more.
- **Real LLM latency will dominate.** With a real model, an agent run takes seconds instead of ~0.3 s, so throughput depends on worker concurrency × model latency, and on your provider rate limits.
- **Open finding.** In one earlier PostgreSQL run a single job stalled one worker for ~35 minutes; the batch still completed. The cause was not identified and did not recur in three later runs, one of them with a lock watcher. Since then every PostgreSQL connection sets `lock_timeout` (30 s) and `idle_in_transaction_session_timeout` (5 min), so such a wait now fails and the job is retried instead of hanging.

## Hardening checklist

- [ ] Dedicated DB role with RLS enforced; audit table append-only
- [ ] Secrets manager wiring; `ENCRYPTION_KEY` rotation runbook tested
- [ ] OIDC enabled, local password login disabled
- [ ] Per-integration webhook secrets set; `WEBHOOK_SIGNING_SECRET` only as fallback
- [ ] Tenant retention set (`retention_days`) and legal review of audit retention
- [ ] Emergency disable drill: Admin → Tenant → emergency_disabled stops all agents immediately
- [ ] Container runs as non-root (Dockerfile) with read-only FS except `/app/storage`
- [ ] Egress allow-list for live providers only (api.hubapi.com, slack.com, api.sendgrid.com, *.atlassian.net, *.myshopify.com, graph.facebook.com, *.zendesk.com, api.anthropic.com / api.openai.com)
